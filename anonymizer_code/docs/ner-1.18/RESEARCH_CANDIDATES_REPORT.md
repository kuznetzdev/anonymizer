## Отброшенные или объединённые идеи до сдачи

Отдельных отклонённых фрагментов в JSONL нет. На этапе разработки отклонены повторения этих уже присутствующих в авторском корпусе **шаблонных идей**:

1. «Паспорт анализатора + тот же код как серийный номер»: текущие `OTHER_DOCUMENT_ID` заменены независимыми жанрами протокола/публичного приказа (`011/046`). Аналогичный мотив встречался в разрешённой к просмотру авторской части `numeric_cases.py`.
2. «Номер полиса ОМС дословно повторён как номер образца»: остались разные роли с различными учебными значениями, без искусственного повторения идентичной длинной последовательности.
3. «Боткин как врач, улица и заболевание в одном абзаце»: в действующей авторской части `mixed_cases.py` этот приём уже применён. Вместо очередной вариации выбраны четыре других эпонима.

Проверены известные мотивы и видимые авторские `CASES` в основных `mixed_cases.py` и `numeric_cases.py` без открытия старых test/challenge. **Полное автоматическое cross-corpus сравнение по всем авторским CASES ещё не проведено**; до принятия куратор обязан завершить независимое сопоставление с разрешёнными train/validation-авторскими записями.

## Спорные границы и вопросы политики

1. **`OTHER_DOCUMENT_ID`** распространяется и на документ оборудования или публичный приказ, если явно назван номер документа. Простой серийный номер самого оборудования остаётся без метки. Для `011/046` `leave` обоснован отсутствием человека.
2. **Общий и личный `EMAIL/PHONE`** получают одинаковый NER-класс. В `018/021` решение указано по конкретным значениям через `span_values`. Перед внедрением маскирования интерфейс решения должен уметь адресовать конкретные упоминания, иначе есть риск скрыть публичную справочную почту.
3. **`DISEASE`** размечается и для цитаты, подозрения, отрицания, учебного термина. Для всех восьми кейсов решение `manual_review`. Требуется постановление владельца продуктовой политики: когда сохранять, маскировать либо обобщать заболевание.
4. **Публичный `COUNTRY/REGION/LOCALITY/STREET/HOUSE`** размечается как лингвистическая сущность, но решение `leave` при отсутствии связи с человеком. Для связанного адреса `mask` назначен компонентам отдельно.
5. **Форматы `X`, `TEST`, `ТЕСТ`** намеренно отличают реквизиты от действительных. Их чрезмерная искусственность снижает представительность NER. При редактуре нужно оценивать жанровую ценность, а не считать X-плейсхолдеры доказательством переноса на реальные OCR-документы.
6. **Статусы идентификации:** прямое сочетание с `PER` оценивается как `text_internally_linkable`; отдельный документный идентификатор без имени требует внешнего регистра, поэтому `requires_external_information`; публичные сведения без персональной привязки относятся к `none`.
7. **Граница medical-risk:** `sensitive_health_present` относится к упоминанию состояния пациента/члена семьи, а учебный эпоним без человека не образует сведения о чьём-либо здоровье.

## Незакрытые направления

- `INN/KPP/OGRN` рядом с владельцем организации, но с чётким разделением корпоративных и персональных реквизитов.
- Пара «одинаковая последовательность цифр одновременно документ/техника» без повторения известных шаблонов из `numeric_cases.py`.
- Естественность OCR-искажений на стыке колонок без подмены реальных реквизитов.
- Независимая представленность новых пяти документных меток в различных жанрах после решения вопроса о тестовых заполнителях.
- Ручная проверка русского написания редких эпонимов и политики маскирования `DISEASE`.
- Семейные отношения, возраст, дата рождения, профессия, редкое событие и дата события остаются за пределами текущих 22 меток; см. 6 карточек `coverage_gaps.jsonl`. **Эти карточки нельзя включать в отрицательный train без решения владельца политики.**

## Приёмка и дальнейшие действия

1. Выполнить `python anonymizer_code/scripts/ner_1_18/validate_research_candidates.py` из корня репозитория. В ходе подготовки проведена независимая структурная проверка содержимого JSONL на действующие метки, уникальность, покрытие решений и контрастные семейства; запуск добавленного Python-скрипта в окружении GitHub не подтверждён.
2. Куратор проверяет реальные границы spans, связанность признаков, контраст и репрезентативность. Для каждого ID: `accept/rework/reject` с причиной; отдельно решает спорные `manual_review`.
3. Проверить семантическое сходство с **разрешёнными** авторскими train/validation `CASES`. Отклонённые и повторяющиеся записи не обогащать ради плана 24–30.
4. Только принятые **семейства целиком** распределять между train/validation без разрыва контрастных пар.
5. Встраивать вручную проверенные разметки в авторский `CASES` и собирать JSONL штатным генератором символьных смещений. Ручные смещения не вводить. Test/challenge не создавать и не использовать.

**Никаких выводов об улучшении F1, отсутствии утечек или полной анонимности эта партия не подтверждает.**
