# Проверка укрупнения классов документов

## Протокол

Это отдельный однократный development-эксперимент для выбора границ классов. Официальный корпус 1.18.1 и его кандидат остаются неизменными.

Проверяемая схема сохраняет 17 прежних классов и добавляет общий `DOCUMENT_ID`. Пять новых классов 1.18.1 (`OMS_POLICY_ID`, `MEDICAL_RECORD_ID`, `REFERRAL_ID`, `DRIVER_LICENSE_ID`, `OTHER_DOCUMENT_ID`) отображаются в `DOCUMENT_ID`. `PASSPORT` и `SNILS` сохраняют прежние классы. Текст и смещения сущностей не меняются.

В полной corrected validation 1.18.1 поддержка (сущности / документы) для этих классов: `OMS_POLICY_ID` — 1/1, `MEDICAL_RECORD_ID` — 3/2, `REFERRAL_ID` — 1/1, `DRIVER_LICENSE_ID` — 1/1, `OTHER_DOCUMENT_ID` — 10/10. После отображения общий `DOCUMENT_ID` имеет 16 сущностей в 15 документах. Эти числа пересчитаны по разрешённому validation-файлу и описывают только development-выборку.

На копиях train и validation 1.18.1 обучается один candidate с feature version 3 и штатными параметрами `train_model`: 3 эпохи, `random_state=17`, `log_loss`, `alpha=1e-5`, `average=True`, batch size 4096. Примеры не добавляются, пороги не подбираются, повторные варианты не запускаются.

Сравниваются candidate укрупнённой схемы, кандидат 1.18.1 со сведёнными к `DOCUMENT_ID` выходами и baseline 1.16. Проверяются общая validation, медицинская validation 1.16.0 и исправленная validation 1.18.1. Для всех моделей приводятся exact-span F1 и доля документов с непокрытой PII-сущностью; отдельно считается результат на прежних 17 классах. `DISEASE` остаётся в exact-span метрике, а disease-only документы исключаются из PII-утечки согласно действующему режиму сохранения заболеваний.

Пути development-входов перечислены явно в `scripts/ner_1_18/taxonomy_ablation.py`. Запуск не читает test/challenge-файлы и их метаданные. Снимок и SHA-256 входов записываются до обучения в игнорируемую директорию `references/evaluations/medical-1.18.2-taxonomy-ablation-corrected/`; существующая директория блокирует запуск.

## Результат

**HOLD.** Укрупнённый candidate показывает смешанную картину: на медицинской validation его legacy-метрика лучше baseline 1.16, а на общей validation он уступает исходному 1.18.1. На объединённый `DOCUMENT_ID` в полной validation приходится 16 сущностей в 15 документах; candidate покрывает 8/16. Текущая модель 1.18.1 после сведения тех же выходов тоже покрывает 8/16, поэтому обучение общего класса не показало прироста обнаружения документов.

PII-утечка — доля документов с хотя бы одной незакрытой сущностью из выбранного набора классов. Для legacy-строк из эталона и предсказаний исключены `DOCUMENT_ID`; в 18-классовом срезе учитываются все обобщённые документные идентификаторы. `DISEASE` остаётся в exact-span F1, а disease-only документы не входят в PII-утечку. Это development-сравнение, без оценки test/challenge.

На общей validation candidate покрывает 62/197 сущностей `DISEASE`; baseline 1.16 — 73/197, а 1.18.1 — 66/197. Для обоих новых кандидатов это хуже установленного предела снижения в 2 п.п. Поэтому вывод по таксономии — оставить родительскую маршрутизацию `DOCUMENT` и конкретные дочерние метки, а не заменять их одним выходом `DOCUMENT_ID`: такая схема сохраняет триаж и тип документа, а проверенный общий выход не повысил покрытие. Решение оставить отдельные листовые метки сохраняет разметочную информацию; слабая поддержка редких типов остаётся ограничением, которое эти development-данные не устраняют.

Выполнен один запуск на 13 731 train-записи и 2 218 validation-записях, feature version 3, 3 эпохи, `random_state=17`, `log_loss`, `alpha=1e-5`, `average=True`, batch size 4096. Не добавлялись примеры, пороги не менялись, второй вариант таксономии не обучался. Входной снимок и результаты лежат в игнорируемой папке `references/evaluations/medical-1.18.2-taxonomy-ablation-corrected/`; manifest фиксирует revision `a67345d708424207d023b9036b29dce02fd6b60b`, версии библиотек и SHA-256 всех входов. SHA-256 candidate: `679278570ca7561a00669a5ddf9f16658d001a96fc604f64739c9ce5609fefcf`.

В первом запуске обнаружена ошибка legacy-среза: он исключал новые классы из предсказаний, но оставлял их в gold. Тот запуск остановлен до записи артефакта и отчёта; исправленный scorer фильтрует обе стороны по выбранным классам. Его тест исключения `DOCUMENT_ID` из legacy-разметки проходит. Неполный входной снимок первого запуска сохранён отдельно и не использовался повторно.
