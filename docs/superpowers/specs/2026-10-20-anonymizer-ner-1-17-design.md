# Anonymizer NER 1.17.0 — архитектурная спецификация

## Цель

Подготовить экспериментальный корпус Anonymizer NER 1.17.0 и проверить, снижает ли кандидат долю документов с незамаскированными целевыми сущностями относительно frozen candidate 1.16.0. Приоритеты: document leak rate, восстановление покрытия `SNILS`, затем ошибки `PER`, `DISEASE`, `STREET`, `INSTITUTION`, `ORG`, `PASSPORT` и адресных компонентов. Неподтверждённый результат остаётся `HOLD`.

## Подтверждённое состояние

- Последний локальный релиз корпуса — `references/corpora/anonymizer-ner-hardcases/1.16.0/`; 1.16.0 содержит 8 384 train, 1 141 validation и 160 test записей, а также sealed challenge из 64 записей.
- 1.16.0 прошла структурную проверку, редакторскую проверку и проверку импортёром. Её development gate получил `HOLD`: document leak на медицинской validation снизился на 0,60 п.п. при минимуме 1 п.п.; покрытие `SNILS` снизилось на 2,04 п.п. относительно 1.15.0. Test/challenge 1.16.0 не оценивались.
- Рабочая модель остаётся CPU sparse token classifier `FeatureHasher` + `SGDClassifier`. API принимает до 20 000 символов; `predict()` анализирует весь переданный текст без окон и без обрезки токенов. В существующих тестах нет теста на длинный медицинский документ.
- Frozen candidate 1.16.0 — NPZ SHA-256 `e39ca86b2daa1a3f3e505ca644222e0e148fe4b4a2224b5a6b692188346700ba`, artifact v3 с `combined_features` contract. Для чтения и воспроизводимого сравнения этого baseline нужна версия model code, которая создала v3; текущий `origin/main` поддерживает до artifact v2.
- Исходный checkout содержит незакоммиченные изменения из нескольких областей и локально игнорируемые данные. Работа ведётся в отдельной ветке от проверенного `origin/main`. В неё переносятся только необходимые NER model code и тест для чтения candidate v3; seed, интерфейсные, публикационные и юридические изменения остаются в исходном checkout.

## Архитектура и поток данных

Остаётся текущий генератор синтетических данных и существующий JSONL/ZIP контракт: `manifest.json`, `train.jsonl`, `validation.jsonl`, `test.jsonl`; метки и offsets остаются совместимыми с приложением. Выпуск 1.17.0 создаётся отдельным каталогом на основе разрешённых train/validation данных 1.16.0; каталог 1.16.0 не меняется. Challenge и test 1.17.0 создаются независимо от train и друг от друга, группируются по вымышленным пациентам, сценариям и шаблонам, проходят слепую структурную и редакторскую проверку, затем замораживаются.

Исходные тексты, train/validation/test JSONL, challenge, веса кандидатов и детализация по примерам остаются в локальном игнорируемом `references/`. Скрипты генерации и оценки, тесты, протоколы и агрегированные PR-отчёты без текстов/предсказаний лежат в отслеживаемых путях `anonymizer_code/scripts/`, `anonymizer_code/backend/tests/` и `anonymizer_code/docs/ner-1.17/`.

Кандидат использует существующую модель и trainer. Baseline и candidate обучаются либо восстанавливаются при одинаковой зафиксированной конфигурации, кроме состава train. Validation разрешена только для разработки и выбора кандидата. Закрытые test/challenge 1.16.0 не читаются для настройки. Challenge/test 1.17.0 оцениваются ровно один раз после фиксации baseline, candidate, кода, конфигурации, протокола и хешей.

## Данные, приватность и источники

- Сохранять ровно 17 существующих меток; не вводить новые классы.
- Использовать только вымышленные записи и идентификаторы. Не помещать тексты закрытых выборок в отчёты или логи; до frozen оценки отчёт содержит только агрегаты и хеши.
- Разнообразить многострочные медицинские документы, повторные упоминания пациента, падежи ФИО, контрастные эпонимы, отрицательные контексты, адреса, форматы паспортов/идентификаторов, валидные/невалидные checksum-ы и отдельные OCR-искажения. Негативная запись не содержит ни одной из 17 меток.
- Не устанавливать сторонние наборы по умолчанию. Для первичных источников составить реестр назначения, лицензии, коммерческих/ML прав, ограничений распространения и наличия реальных ПДн. Импортировать данные только после положительной проверки прав и конкретной оценки вклада.
- Качество важнее квоты. Ориентир — 1 200–1 500 новых train записей; объём уменьшается, если новые записи повторяют шаблоны или требуют сомнительной разметки. Независимая редакторская проверка охватывает все held-out записи и не менее 50 новых train записей, включая каждую группу сценариев.

## Оценка и заранее зафиксированные ворота

Основная метрика — document leak rate: доля документов с gold-сущностью, в которых предсказанная маска оставляет непокрытый gold span. Публиковать support и считать exact span/type precision, recall и F1 (micro и по классам), любое покрытие gold span, false-positive spans, лишне удалённые символы, длинные документы и OCR отдельно. Для `DISEASE` отдельно оценивать классификацию и не считать её автоматически утечкой ПДн.

**Development gate до freeze:** на общей и медицинской validation exact micro F1 не ниже baseline более чем на 0,01, document leak rate не хуже более чем на 0,01, покрытие целевых классов не хуже более чем на 0,02. Для допуска к freeze document leak на medical validation должен улучшиться минимум на 0,01. Покрытие `SNILS` должно вырасти минимум на 2 п.п. относительно candidate 1.16.0 и восстановиться минимум до candidate 1.15.0 на той же validation: не ниже 45/49 (91,84%). Если условия не выполняются, gate остаётся `HOLD`.

**Новый independent challenge:** document leak должен снизиться минимум на 0,05 абсолютной доли; покрытие каждого целевого класса не должно упасть более чем на 0,05; лишне маскируемые символы не должны вырасти более чем на 20% относительно baseline. Для значимого сравнения каждый целевой класс должен иметь поддержку не менее 30 gold spans; иначе результат по классу обозначается low-support и не может служить PASS.

**Новый frozen test:** exact micro F1 не падает более чем на 0,01, document leak rate не растёт более чем на 0,01, покрытие каждого целевого класса не падает более чем на 0,02, лишне маскируемые символы не растут более чем на 20%. Каждый класс также показывает support; низкая поддержка не трактуется как доказательство безопасности.

Любой провал независимого порога или недостаточная поддержка ключевого класса означает `HOLD`. После вскрытия 1.17 challenge/test запрещены изменения кандидата и повторная оценка на тех же выборках. Для следующего цикла создаются новые held-out выборки.

## Длинные документы и интеграция

До изменения inference проверить длины до API ceiling 20 000 символов, сохранение всех сущностей и глобальных Unicode offsets, повторные ID, последние строки и маскирование результата. Текущий sparse classifier не имеет лимита токенов, поэтому chunking и offsets не добавлять без воспроизводимого дефекта или измеримого ограничения. Если выявлена необходимость изменения API ceiling/инференса, оформить её отдельным PR 4 с регрессионными тестами и обратной совместимостью. Кандидат не активировать автоматически; готовый rollback — сохранить frozen artifact 1.16.0 и переключать runtime только явной процедурой приложения.

## Воспроизводимость и приёмка

Для каждого training run фиксировать seed, параметры, порядок и хеши train/validation, версии Python/numpy/scipy/scikit-learn, Git commit, время/ресурсы, артефакт и метрики. Использовать текущий `train_model` и зафиксированный v3 `combined_features` contract, на котором обучен baseline 1.16.0; добавить в PR3 явный параметр выбора v3, сохранив v2 default для существующих callers. Не менять одновременно корпус и алгоритм. Запуск необходимых backend-тестов должен быть воспроизводим в изолированном Python environment или в существующем Docker backend с declared requirements, включая `psycopg`; не добавлять новые runtime зависимости.

Каждый PR включает change report, фактические тесты и критерии PASS/HOLD. Структурный PASS, импорт ZIP и тесты кода не являются доказательством улучшения модели. Интеграционный PR создаётся только при подтверждённой необходимости. Успешное завершение — независимая оценка, прошедшая заранее заданные пороги; иначе документируется `HOLD` с причинами и планом следующего независимого эксперимента.
